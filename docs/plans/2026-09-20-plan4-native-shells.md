# Plan 4 — Reproducible native shells (optional track)

**Status:** Planned; no native release is verified by this document.

**Goal:** Package the proven Pantry Pal web experience for iPhone/iPad, Android, and selected desktop platforms, with reproducible builds, reliable authentication returns, usable camera flows, and recorded release evidence.

**Depends on:** P0's Cloudflare migration contract (Workers API, D1 identity/session and household mapping, R2 photo access, authentication library/provider, credential transport, migration/cutover rules), and P3's responsive/PWA acceptance baseline. This is an optional parallel track after P3; native signing or store access must not delay the web release or the remaining web plans.

**Architecture:** Preserve Next.js static export in `out/`, Capacitor for iOS/Android, and Tauri for desktop. Replace the legacy backend with the Cloudflare Workers API and D1 identity/session/data contract from P0; use R2 for approved photo storage. The web export can remain on Pages initially, with a same-origin API/auth route, or be served through Workers Static Assets under P0's deployment decision. Native shells bundle the export and call the explicit HTTPS API origin. Keep product logic shared; isolate native integration behind small platform adapters. No Supabase SDK, Auth, hosted database, storage, or credentials remain in the target native runtime.

## Execution rules

- Make one logical change per commit, with targeted tests for observable behavior. Run `npm run typecheck`, `npm test`, and `npm run build` before integrating shared application changes; preserve the earlier plans' additional gates.
- Develop against nonproduction test accounts and fictional pantry data. Bundled web/native code is public: include only the API origin and public application identifiers, never Cloudflare API tokens, D1/R2 credentials, authentication secrets, signing keys or a confidential OAuth client secret. Workers must validate each session/token and authorize every household operation using the verified identity and D1 membership; never trust a client-supplied household ID as authorization. D1 is the backend database, not a public client authorization service. [D1 overview](https://developers.cloudflare.com/d1/).
- Record exactly which platforms, OS versions, devices and build modes passed. Simulator/emulator success and desktop browser emulation are not physical-device camera or installed-app evidence.
- Keep PWA installation separate from offline readiness. Current Chrome promotion criteria do not require a service worker; an install button alone proves neither offline startup nor safe updates. See [Chrome install criteria](https://web.dev/articles/install-criteria).
- Do not replace Capacitor with a Trusted Web Activity by default. TWA is an Android browser-rendered hosted-web option with Digital Asset Links and different native/web-state boundaries. Consider it only through a separate ADR comparing a concrete need with the existing Capacitor path. See [TWA overview](https://developer.chrome.com/docs/android/trusted-web-activity).

## Authentication decision inherited from P0

Hosting a domain on Cloudflare does not create consumer accounts, sessions, recovery or household authorization. P0 must select and validate a maintained Workers-compatible authentication library/provider. A concrete candidate is Better Auth, whose official release documentation describes native D1 support; validate the exact pinned version, required plugins and Workers behavior rather than assuming every plugin supports D1. The maintained OAuth Provider plugin documents public/native clients, authorization-code flow with S256 PKCE, and exact return-URI matching. These are capabilities to evaluate for the native contract, not an instruction to build custom cryptography. [Better Auth D1 support](https://better-auth.com/blog/1-5), [OAuth Provider](https://better-auth.com/docs/plugins/oauth-provider).

Cloudflare Access can be evaluated if the product is expressly a closed, allowlisted household application. It adds a separately configured identity/policy layer and can use an identity provider or email one-time PIN; it is not automatically selected for public consumer sign-up. If chosen, P0 must still define app identity, household membership, revocation and the supported native handoff. Never package an Access service token as a user credential. [Access application setup](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/), [one-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/).

The native contract must distinguish the system browser's session, the local WebView, and the Workers API. Cookies do not automatically transfer between these contexts. Use secure system-browser sign-in and a short-lived, single-use return code bound to the initiating client/verifier through the chosen library's documented authorization-code/PKCE or equivalent native flow. A generic one-time-token plugin does not by itself establish PKCE binding. Resolve this in P0 before implementing native authentication; continue independent packaging work while the contract is settled. [One-time-token capabilities](https://better-auth.com/docs/plugins/one-time-token).

## Task 2 — Define runtime, origin, storage, and service-worker behavior

**Files:** new `src/lib/platform.ts` and behavior tests; `src/components/service-worker-register.tsx` and its tests; P0's replacement API/auth clients (proposed `src/lib/api-client.ts`, `src/lib/auth-client.ts`; use the actual accepted paths); `capacitor.config.ts`; `src-tauri/tauri.conf.json`; `PACKAGING.md`.

- [ ] Add a browser-safe adapter reporting web, Capacitor iOS/Android, or Tauri and the supported capabilities. Avoid user-agent-only detection and do not access native globals during Next build/prerender. Load native APIs only in the relevant runtime.
- [ ] Record actual origins from release builds. Preserve secure/default local serving schemes unless a demonstrated requirement demands a change. Do not equate a local WebView origin with an OS-registered auth return URL; these are separate settings.
- [ ] Use relative API/auth routes for the same-origin web deployment and the configured HTTPS Workers API origin for native packages. Prove API/auth paths reach the handler before any static/SPA fallback; an HTML response is not successful API JSON. Workers Static Assets supports selective Worker-first routing; Pages can remain the initial static host under P0's routing contract. [Worker/static routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/).
- [ ] Enumerate the exact native origins observed on supported release builds and configure explicit CORS/trusted-origin rules for those clients and environments. No wildcard origin with credentials, blanket `null`-origin allowance, or arbitrary origin reflection. Verify preflight, rejected origins, method/header limits and `Vary: Origin` where responses vary. An allowed origin is not authentication; every protected request still requires a validated user session/token. Avoid assuming absent/spoofable native Origin headers prove a trusted app.
- [ ] Keep production Capacitor `server.url` unset, cleartext traffic disabled, and arbitrary navigation overrides absent. Open external content through a constrained external-browser path; do not load remote scripts/pages into a privileged native view as a workaround. Capacitor documents these server overrides as development-oriented. [Configuration reference](https://capacitorjs.com/docs/config).
- [ ] Make P3's web service-worker registration/update policy conditional on the web runtime. Bundled native assets should start from the installed package, without web cache replacement or broad cache deletion. If cleaning a previously installed Pantry worker is necessary, restrict cleanup to identified Pantry scopes/cache names and document the one-time migration.
- [ ] Implement P0's explicit native credential transport and secure-storage adapter, using the chosen auth library's supported access/refresh or session mechanism. Keep system-browser cookies in that browser; do not copy cookie jars or weaken web cookie/CSRF rules to make native requests pass. Verify restart, expiry/refresh, revocation, sign-out, account switch, offline resume, and app upgrade. Store long-lived native credentials in platform secure storage where required by the contract; ordinary WebView storage must not be described as encrypted. Preserve migrated household identity and do not merge accounts by an unverified email match.
- [ ] Test all exported routes and asset URLs in packaged release builds, including nested-route reload, back navigation, sign-in, remote image loads, and error screens. Do not repair missing local routes by adding a live development server.
- [ ] Prove that a network outage preserves the P3-approved local behavior and clearly labels unavailable remote operations. Never report queued work as synchronized before acknowledgment.

**Acceptance:** Web behavior remains unchanged by native detection, each native shell boots its bundled assets, API origins and credential transport are explicit, rejected origins/invalid credentials fail closed, and no native runtime deletes unrelated caches. Next static export cannot provide request-time headers, Proxy, or Server Actions; keep remote work in Workers under P0's contract. [Static export limitations](https://nextjs.org/docs/app/guides/static-exports).

## Task 3 — Complete authentication return paths

**Files:** `src/lib/auth-context.tsx`, P0's replacement API/auth clients and Workers auth handler; new `src/lib/auth-redirect.ts` with tests and a native lifecycle component; iOS `Info.plist`/entitlements, Android manifest/string resources or their owned templates; `src-tauri/src/lib.rs`, `src-tauri/capabilities/default.json` and Tauri configuration only for desktop return integration; new `docs/native/auth-returns.md`. Coordinate changes to P0-owned Worker/auth files through its accepted contract.

- [ ] Read P0's identity migration and auth decision before choosing a flow. Inventory the methods actually supported by the replacement library/provider and the account re-enrollment/recovery policy; a legacy password login is not proof that its stored credentials migrate. Preserve the approved user-facing methods and household identity mapping. Record unshipped methods as out of scope.
- [ ] Specify return URLs for development, preview/test, web production, and native release. Prefer verified HTTPS app/universal links when feasible; document a tightly scoped custom-scheme alternative where needed. Prepare the exact Workers/auth-provider redirect allowlist, public native-client registration and domain-association files before any external configuration request. Never broaden production redirects to an unrestricted wildcard merely to make a test pass.
- [ ] Start native sign-in in the platform system browser with fresh state and the chosen library's documented verifier/challenge binding. On successful browser authentication, return only a short-lived, single-use authorization code and correlation state to the registered native callback. Exchange it over HTTPS using the originating verifier and the correct client/redirect binding; do not place access/refresh/session tokens in the callback URL, logs or analytics. Do not add a reusable client secret to a mobile/desktop package. Use maintained library/provider protocol handling and tests rather than a new homegrown token protocol.
- [ ] Register the selected return mechanism in the native project and handle both warm-open events and cold-start launch URLs. Capacitor's App plugin provides `appUrlOpen` and `getLaunchUrl`; remove listeners on teardown and deduplicate the same callback. Do not log callback URLs or token payloads. [App plugin](https://capacitorjs.com/docs/apis/app), [deep-link configuration](https://capacitorjs.com/docs/guides/deep-links).
- [ ] Validate callback scheme/host/path, issuer where applicable, and flow-specific state before processing. Preserve the verifier only for the intended pending flow, perform the library/provider exchange once, and reject mismatched-client, wrong-verifier, malformed, expired or replayed codes. Prove single-use redemption is atomic under concurrent requests in the chosen D1-backed implementation. Remove sensitive URL/history material after processing; never accept an arbitrary user ID from the native callback as an authenticated identity.
- [ ] Test confirmation while foregrounded, backgrounded, and fully closed; canceled browser return; missing app; expired link; mismatched callback; repeated callback; offline callback followed by retry; sign-out/account switch. Include an explicit path for a link opened on a different device where a local verifier cannot be available.
- [ ] For desktop, implement the equivalent constrained open/return path only with scoped Tauri capabilities. Verify packaged behavior on the target OS; development URL handling is insufficient. Keep the shared callback parser separate from the OS event adapter. [Tauri deep links](https://v2.tauri.app/plugin/deep-link/).
- [ ] After a valid return, verify session persistence and a Workers-authorized household read/write with test data, then confirm a different household is denied. Test refresh-token/session revocation and logout according to P0, including an already-open second device. A window opening is not an authentication test. Keep auth/lifecycle callbacks cancellable, bounded and free of duplicate requests or locks that stall resume.

**Acceptance:** All shipped methods complete safely on each supported shell, including cold start, and unauthorized/malformed returns cannot change session or household. The Workers API validates the resulting credential and enforces D1 membership on every operation. Browser and native credential transport are separately tested, with no dependence on cross-site cookies automatically appearing in the local WebView. [Public/native authorization-code flow reference](https://better-auth.com/docs/plugins/oauth-provider).
